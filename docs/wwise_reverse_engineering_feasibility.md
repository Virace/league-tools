# Wwise 黑箱转白箱可行性记录

本文档记录一个待定但可行的研发方向：通过构造可控的 Wwise 工程样本，把当前依赖“真实游戏样本 + `wwiser` XML 反推”的黑箱调试方式，逐步变成可验证、可复现的白箱实验链路。

这不是当前仓库的既定开发路线，也不是近期必须完成的任务。它的目标是说明：

- 为什么这条路值得做
- 进入这条路之前需要补哪些前置认知
- 真正开始实验时，最小可行闭环应该怎么搭

## 1. 为什么值得做

当前针对 `BNK` / `HIRC` / 音乐容器的排查，主要依赖：

1. 游戏内真实 `events.bnk`
2. `wwiser` 导出的 XML
3. 对 `Event -> Action -> Container -> Track -> sourceID` 链路的人工比对

这种方式能解决具体问题，但有两个明显成本：

- 一旦遇到 `MusicSwitch`、`MusicRandom/Sequence`、`MusicSegment` 这类音乐对象，内部字段含义往往只能从样本中倒推。
- 当真实游戏样本同时混合多个容器、状态参数、切换规则和过渡对象时，很难判断某个字段到底影响的是哪一层关系。

如果能构造“我们自己知道正确答案”的最小 Wwise 工程样本，再用 `wwiser` 反编译，就能把下面这些问题从“猜测”变成“验证”：

- 某个容器对象到底应该产出哪些 `child_ids`
- `MusicSwitch` 的 `pNodes` / `pRules` / `pArguments` 哪些字段只影响选择规则，哪些字段决定遍历目标
- `MusicRandom/Sequence` 的 `pPlayList` 中哪些 `SegmentID` 应当继续向下追
- `MusicTrack` 中哪个字段稳定对应最终音频资源 `id`

## 2. 当前主要难点

这条路线的真正成本不在代码，而在工具与领域认知。

### 2.1 Wwise 本身学习成本高

Wwise 是完整的音频中间件，不是只看一个导出按钮就能上手的资源打包器。对于当前仓库最相关但也最陌生的部分，至少包括：

- 事件、容器、Track、Segment、Switch、State 在编辑器中的概念映射
- 资源导出后 `BNK` / 媒体文件的组织方式
- 游戏内使用的工作流与 Wwise 默认工作流之间是否存在 Riot 自己的约束

## 2.2 需要先估计游戏使用的 Wwise 版本

最自然的入口不是先创建工程，而是先回答：

```text
游戏里的 BNK 版本更接近哪一代 Wwise？
```

这一步不能保证“一定精确反推到唯一 Wwise 版本”，但可以先把范围收窄到一个可实验的版本区间。

建议的顺序是：

1. 从 `BKHD` / `HIRC` 中稳定读取游戏样本的版本号。
2. 把版本号与公开资料、`wwiser` 支持情况、社区已有解析器实现做交叉对照。
3. 优先选择最接近、且 `wwiser` / 本地环境都能稳定工作的版本做实验。

## 2.3 软件内部概念映射不直观

即使打开了 Wwise，仍然有一个难点：

```text
事件 / 容器 / 音频资源在软件里分别对应什么视图、什么节点、什么导出结果？
```

如果这一层概念没有搞清楚，很容易出现“能导出 bank，但不知道自己验证了什么”的问题。

因此，真正开始实验前，最好先完成一份极简概念对照表：

- Event 在 Wwise 中长什么样
- Action 在导出产物里如何体现
- MusicSwitch / MusicRandom / MusicSegment / MusicTrack 分别对应哪些层级
- 最终音频资源 ID 在编辑器里是否可控、是否可追踪

## 3. 建议的最小可行实验闭环

如果未来决定做这条路线，建议不要一开始就碰复杂工程，而是按最小矩阵推进。

### 阶段 A：先验证“单链路可控”

每个样本只保留 1 个事件，且下游音频资源尽量唯一、可辨识。

建议顺序：

1. `Event -> Action -> Sound`
2. `Event -> Action -> Random/Sequence -> Sound`
3. `Event -> Action -> MusicTrack`
4. `Event -> Action -> MusicSegment -> MusicTrack`
5. `Event -> Action -> MusicRandom -> MusicSegment -> MusicTrack`
6. `Event -> Action -> MusicSwitch -> MusicRandom -> MusicSegment -> MusicTrack`

目标不是做出“像游戏一样复杂”的 bank，而是先回答：

- 每一层对象在 `wwiser` XML 里长什么样
- 我们真正需要读取的是哪几个字段
- 哪些字段只是编辑器/运行时行为参数，与“事件到资源 ID 映射”无关

### 阶段 B：再单独补 transition / state / switch rule

等最短链路确认后，再引入：

- `transition`
- 多个 switch state
- 多个 destination
- 带权重的 random/playlist

这样才能把复杂度控制住，不会在第一轮就把“结构问题”和“规则问题”混在一起。

## 4. 对当前仓库的实际帮助

如果这条路线跑通，最直接的收益有 3 个：

- `native_hirc` 的跳读顺序可以不再主要依赖第三方实现对照，而能依赖我们自己的实验真值。
- `WwiserHIRC` 中音乐容器解析可以从“够用就行”升级到“知道为什么这样取字段”。
- 遇到后续新的 `MusicSwitch` / `MusicTrack` 异常时，可以先在最小样本里验证，再决定是格式分支问题、版本问题，还是单个游戏 bank 的特殊结构。

## 5. 当前建议

在真正投入 Wwise 学习成本之前，当前更推荐的顺序是：

1. 继续基于真实游戏样本修复当前解析链。
2. 顺手把遇到的关键样本、关键 XML 片段、关键对象链记录下来。
3. 等音乐容器类问题积累到一定数量，再决定是否正式投入“黑箱转白箱”实验。

换句话说，这条路线是合理的，但它更像一个“中期研发投资方向”，而不是当前每次修 Bug 都必须先走的门槛。
